02 · 步骤复现步骤（都集中在仓库的 scripts/ 下）

1. ROCm 版 PyTorch（Windows 原生，不需要 WSL、HIP SDK） 
uv venv .venv --python 3.12 --seed
.\.venv\Scripts\python.exe -m pip install --index-url https://repo.amd.com/rocm/whl/gfx1151/ ^
    "torch==2.11.0+rocm7.13.0" "torchvision==0.26.0+rocm7.13.0" "torchaudio==2.11.0+rocm7.13.0"
2. ComfyUI v0.35.0（原生支持 H3，comfy-kitchen 0.2.33 的 hip 后端下 INT8 可跑） 
git clone --depth 1 --branch v0.35.0 https://github.com/comfyanonymous/ComfyUI.git
pip install -r ComfyUI\requirements.txt   # 安装时去掉 torch 三行，再从 AMD index 重装 torch
3. 模型（Comfy-Org/MiniMax-H3，约 58 GB + ref2va 21 GB） 
.\scripts\download_models.ps1 -Ref2VA
4. 启动与生成 
.\scripts\run_comfyui.ps1      # --highvram --bf16-unet --use-ck-attention --disable-pinned-memory --reserve-vram 2
.\.venv\Scripts\python.exe -m h3gen gen --prompt "..." --width 832 --height 480 --seconds 5 --steps 8

scripts/setup.ps1 把第 1〜2 步一次做完。h3gen 按官方模板的节点图（UNETLoader → Turbo LoRA → BasicGuider / BasicScheduler(res_multistep, simple) → SamplerCustomAdvanced → VAEDecode + VAEDecodeAudio → CreateVideo 24 fps → SaveVideo）组装成 API 格式，并用 WebSocket 的 executing 事件间隔记录各节点耗时（与文章中 profile_nodes.py 思路相同）。

  • INT8 attention（ComfyUI 的 --use-ck-attention / ModelAttentionBackend）：comfy-kitchen 的 hip 后端使用 gfx1151 的 WMMA，相比 pytorch SDPA（aotriton）快 2.6 倍（71.4 → 27.8 s/step）。同一随机种子下画质相当。
  • 仅首次需要加载模型（TE 26 GB + DiT 20 GB + VAE 5.5 GB ≈ 60〜90 s）。之后由 --highvram 常驻。峰值 VRAM 约 78 GB，单进程可分配上限约 85 GB。
  • VAE 解码占整体的 20〜25 %（832×480×124f 时为 59 s）。与文章中「采样 84 % / VAE 11〜17 %」的趋势一致。
  • 在 ROCm 10.0.0（torch 2.13, 2026-08 GA）下同样可用：采样慢约 10 %，VAE 解码快约 16 %。默认为稳妥起见仍用 7.13。
  • 参考：文章中 RTX 5090 生成 1280×704 的 12 秒级片段只需 79 s。本机 832×480 · 5 秒约需 285 s —— 大约慢一个数量级，但完全本地运行，并且能用 96 GB 统一内存把 33B 模型整体常驻。

05 · 应用AI 电视台（aitv）

本地 LLM（Ollama / gemma4，跑在 CPU 上把 iGPU 让给 H3）按节目格式（新闻 / 天气 / 自然纪录片 / 广告 / 料理 / 音乐 / 台标 ID）分别写出 H3 格式的提示词 JSON，由 h3gen 提交给 ComfyUI，再用 ffmpeg 规范化为 H.264/AAC 后加入素材库。Web 播放器按新到顺序连续播放，ffmpeg 的 HLS 广播进程通过 /hls/live.m3u8 持续推流 24 小时。

节目单(加权随机) ─▶ LLM 台本 (JSON: title / segments[caption, seconds, prompt])
                              │  自动补正 <d>[Japanese] …</d>
                              ▼
                     h3gen → ComfyUI (/prompt, /ws)  ── 832×480 · 8-step turbo · INT8
                              │  ~5 分 / 6 秒片段
                              ▼
               ffmpeg normalize → aitv/library/*.mp4 + index.json
                              │
              ┌───────────────┴───────────────┐
              ▼                               ▼
   aitv.server :8800  (播放器)          aitv.hls (ffmpeg -re → HLS)
   /playlist.json, /clips/…            /hls/live.m3u8  (VLC / OBS / hls.js)

24 小时运行的真实情况

制作速度约为实时的 1/60（6.6 秒的片段约需 400 秒），所以跑满一天也只有约 25 分钟新内容。作为电视台不停播，与每天能产出 24 小时新内容，是两回事，后者在这块 GPU 上做不到。播出侧按「优先立即播出从未播过的片段（从新到旧）→ 若没有，则在避开近期播过的内容下，按越新权重越高的随机选择」的顺序编排，使其看起来不像固定循环（aitv/hls.py: pick_next，播放器同策略）。用 scripts/run_station.ps1 常驻启动 ComfyUI、播放器、HLS 与制作循环（-Status / -Stop / -Restart）。

按连续运行数天的前提评审了代码，修掉了确认存在的问题。主要有：HLS 编码器挂掉时 remux 失去排出口而阻塞、无法进入恢复流程；-fflags +igndts 压坏了片段边界之后的时间戳（实测 71 % 的帧，改为只用 +genpts 后恢复到 1/24 秒粒度）；index.json 替换时因 Windows 共享冲突失败，导致耗时约 400 秒的片段进不了索引；HIP 挂起时 /system_stats 仍然应答，使生成无限期卡住（增加了无响应超时与 /interrupt）；停止脚本按命令行子串匹配，误杀了无关进程。详见 docs/aitv.md。

06 · 经验踩坑记录

  1. PYTORCH_HIP_ALLOC_CONF=expandable_segments:True 在 Windows/HIP 上禁止使用。 明明还空着 94 GB，加载文本编码器时却在 13〜14 GB 处 OOM。通过二分查找环境变量定位（scripts/vram_probe3.py）。换成默认分配器后可分配到 85 GB。
  2. nvfp4_awq 文本编码器是 NVIDIA 专用的。 虽是官方模板的默认值，但 hip 后端没有 nvfp4 内核。AMD 上应使用 int8_convrot 版（27 GB）。
  3. HF 上的 Comfy-Org/MiniMax-H3 没有 split_files/ 前缀。 直接位于 diffusion_models/, text_encoders/ 之下。
  4. pip 会把 torch 换成 CUDA 版。 安装 requirements 时去掉 torch 三件套，再从 AMD index 重装来保证。
  5. ComfyUI 的 /view 下载在本地不要用。 aiohttp 的 sendfile 在 Windows 上会挂，而且写到与输出相同的路径会把生成物截成 0 字节（实际踩过）。本地直接引用输出目录。
  6. 卸载量化模型会触发 access violation（ROCm 10.0）。 /free → INT8 张量 GPU→CPU 搬运时整个服务端崩溃。fl2va ↔ ref2va 的切换改为重启服务端。
  7. 同一个图会被 ComfyUI 缓存并 0 秒返回。做基准时要换随机种子。
  8. 画面内的日文字符会崩（天气图的标题等）。字幕改为在后段用 ffmpeg 叠加。
